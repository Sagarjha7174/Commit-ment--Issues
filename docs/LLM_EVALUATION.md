Every answer goes through the FastAPI app (`/explain`, `/whatif`) on the real engine.

## Metrics and targets

- **Groundedness**: share of numbers in the answers that match an engine value (target ≥ 90%).
- **Factual accuracy**: share of cited values equal to an engine value recomputed independently by a fresh `scenario_builder.build` (what-if differences from the two results), with a consistent display (target ≥ 90%).
- **Unsupported-claim rate**: share of answer sentences carrying a number that matches no engine value (target < 5%).
- **What-if success**: right outcome, right `ScenarioRequest` change, engine rerun (new scenario id) or correctly not rerun, right measures added / removed / blocked.
- **Refusal correctness**: refused exactly when expected (out of scope, invalid request).

## Changes after the first run (disclosed)

The first template run passed 96.2% of items with factual accuracy 93.2%. These were fixed after seeing them, so the set is no longer strictly held out for these behaviours:
- Factual accuracy: cited per-measure step savings and the after-retrofit emissions (used by what-if differences) were engine values missing from the payload, so the independent check could not match them; the payload now includes them (a payload completeness fix; no displayed number changed).
- q31 (*"electricity cost 20p per kWh and gas 6p per kWh"*): the keyword parser gave both prices to gas; it now takes the fuel named in the price's own clause (a parser bug).
- q53 (injection): the item's regex rejected any "guarantee", but the answer correctly says the figures are "not guarantees"; the regex now only rejects an unnegated guarantee (an evaluation-set bug).
- After the first mocked-LLM run: the checker now always requires the list of missing details when details are missing (q46: a 'score not available' sentence alone had satisfied coverage); and the mock's parser now reads situation statements like a real parse model (q40, a mock-fidelity fix, no system change).
No other item, prompt or rule was changed after the first runs.

## How grounding works

- The LLM never sees a number: it writes `{placeholders}` that code fills from the engine result.
- A rule checker rejects any sentence with a typed number, a wrong direction or an unsupported claim, and fills gaps from the deterministic template.
- An independent number check (`backend/app/llm/numbers.py`) then matches every number in the final text to an engine value. An unmatched number triggers one regeneration with feedback, then the template.
- Without a key, every route answers with the template, so the demo and tests never depend on the network.

## Limits

- The question set is the team's own; it shows the guardrails hold, not real-world answer quality.
- Groundedness and factual accuracy check numbers, not every qualitative statement. An LLM judge (`backend/app/llm/prompts/judge_v2.txt`, from the original layer) can be run on a sample when a key is available.
